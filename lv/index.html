Loop Validation. How my code gets checked now, and why I'm moving off a CI/CD pipeline.

Why I built it

AI coding agents write most of my code now, and they push often. Every push went through a CI/CD pipeline: wait for a machine, run every check, then answer. The agent waited the whole time.

So I moved the check inside the agent's loop: before the push, and only on what the change touches.

What Loop Validation is

My own checker, on my own server. Before an agent pushes, it asks LV to check its work. LV works out what the change touched, runs just those checks side by side and gives one verdict. When the push lands, LV recognises the same code and reuses that verdict, and the merge waits for it.

The name: an agent works in a loop of write, check, fix, repeat. A CI/CD pipeline sits outside that loop, after the push. Loop Validation puts the check inside it.

Moving a repo over

A repo switches when LV and the pipeline agree on at least one replayed commit, disagree on none, and LV never errors. The one exception is a disagreement the repo causes itself, such as a flaky test: it gets explained before the switch, not ignored.

Four of my repos have moved over so far, this site included.

Pros and cons

Better

  • Faster, most of all on a slow day.
  • A change reaches the repo already checked, so fewer fix-and-push rounds.
  • No rented overflow machines to pay for, and nothing checked twice.
  • It watches the live site after each deploy and rolls back a bad one, on this site so far.

Worse

  • One server and no overflow: if it is down or full, checks wait, and keeping it running is my job.
  • Checks that need Docker or a database can't run there yet.
  • Apple app builds take turns on one Mac.
  • Picking only the touched checks could miss something; it runs everything when unsure.

Run each check in a microVMNot yet. Each check runs as a throwaway, locked-down job with capped CPU and memory. The server can now run Firecracker microVMs; they aren't built yet.
Never redo workDone. The same code reuses its verdict, and docs-only changes skip.
Feedback in under a minuteNot yet. A typical check took 1.9 minutes last week; a reused verdict is instant.
Faster type-checking and linting toolsNot yet.
Shared staging with request routingNot built. These are single web apps, so it may not be needed.
Gradual rollout with automatic rollbackPartly. After each deploy of this site, LV watches it for 10 minutes and rolls back a bad one by itself. Other repos aren't opted in yet, and there's no gradual rollout.
A shared record of what agents plan and decideNot yet. LV keeps verdicts, not decisions.
Merge queues and agent-ready source controlSkipped for now.
